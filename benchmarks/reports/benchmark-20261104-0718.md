## Notes

- Nodes run in containers on the MongoDB container's network: Docker Desktop on Windows adds a 40 ms stall to host-to-container requests over ~750 bytes, which would penalise whichever version's saves happen to cross that size.
- Every node is a separate process, started and connected before the workflows are registered. The total time runs from releasing the nodes until the last node exits, which it does once no unsuspended workflows remain.
- Versions from 5.0 use `ExecuteWorkflowsAsync(batch, concurrency)` in a loop (`--mode`). Versions before 5.0 have no async API or `maxConcurrent`, so they call `ExecuteWorkflows(concurrency)`, which loads that many workflows and runs them in parallel, waiting for the whole batch before loading the next.
- Releases before 6.0 have no workflow locking, so two nodes would execute the same workflows - multi-node scenarios are n/a for them.
- Checks: every workflow completed, none active or suspended, no temp files left behind, and no node timed out. A failed check is marked ⚠.
- The actions are synchronous (`IWorkflowAction`) for every version, so differences come from the engine and store, not the action code.
